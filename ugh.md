## 1. Setup and template design drift

- **Initial plan vs reality**
  The original idea was simple: use template files (`scripts/posix_guard.sh.template`,
`scripts/powershell_guard.ps1.template`) and a small
[install.sh](cci:7://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:0:0-0:0) that
would just fill placeholders.
  Over time, more and more logic moved into a dynamic generator inside
[install.sh](cci:7://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:0:0-0:0), and the
  templates effectively became dead code. They stayed in the tree for a while, which made it
unclear which path was actually authoritative.

- **Repo layout noise**
  There was some initial confusion around `makerepo` and where the `no-npm` repo lived, but
that got resolved. It was friction, not a deep bug.

---

## 2. First installer pass: brittle and overcomplicated

- **Misused `sed` with stdin**
  The first `process_template` approach tried to feed multiple fragments into `sed` using `r
  /dev/stdin` several times. That doesn't work: stdin is only consumed once, and the whole
"stream of generated sections" idea was structurally wrong.

- **Template vs generator tug-of-war**
  The code tried to combine:
  - A static template with `{{PREFERRED_PM}}` and similar placeholders
  - A runtime generator that wanted to inject complex logic
  This hybrid made the code fragile and hard to reason about.

---

## 3. Dynamic generator bugs: syntax and escaping

When everything moved to a fully dynamic generator ([generate_guard_script](cci:1://file:///
Users/pcstyle/projects_2/AI/no-npm/install.sh:487:0-667:1) inside
[install.sh](cci:7://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:0:0-0:0)),
several issues surfaced:

- **Bad `case` pattern for blocked PMs**
  The generator initially produced:

  ```bash
  npm)
  pnpm)
  yarn)

  instead of:

npm|pnpm|yarn)

  which is simply invalid shell syntax. This had to be refactored into a single
pipe‑separated pattern.

- Over-escaped function names
Function names like _bun\_equiv were generated by "escaping" underscores that never needed
escaping in the first place. That created invalid function identifiers. Later this was fixed
  to _bun_equiv, _bun_warn, etc.
- Equivalence mapping too npm-centric
Early mapping treated everything like npm and did rough substitutions:

echo "{{PREFERRED_PM}} install ..."
echo "{{PREFERRED_PM}} add $*"

- with no respect for bun's difference between install (graph) and add (packages). This was
later corrected so each preferred PM got its own mapping rules:

  - Bun: no args → bun install, with args → bun add ...
  - pnpm/yarn: separate install/add handling
  - npm: avoids fake npm add, sticks to npm install ...

---
4. Blocked-PM configuration edge cases

- Unnormalized input
The first cut just accepted a comma‑separated string for blocked_pms and trusted it. That
allowed:
  - Invisible whitespace problems
  - Duplicate entries
  - Accidentally blocking the same PM that was supposed to be enforced
- Later fix
The handling was tightened to:
  - Trim whitespace
  - Validate each entry
  - Deduplicate
  - Drop the preferred PM from the blocked list
  - Re‑prompt if the list ended up empty

This should have been the design from the start.

5. TTY requirement and "just echo into it"

- The installer was written to require an interactive TTY:

if [[ -t 0 ]]; then
    interactive_install
else
    echo "This installer requires interactive mode"
fi
- Because of that, piping scripted answers like:

printf '...\n' | ./install.sh --dry-run

- was never going to work, but this trade‑off (TTY only, no scripted stdin) wasn't clearly
documented upfront, which caused confusion when trying to automate tests.

6. Shell detection and the .bashrc vs .zshrc problem

- Root cause
With #!/bin/bash, ZSH_VERSION is empty inside the script, even if it's launched from zsh.
The original cci:1://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:326:0-369:1 logic
  keyed off ZSH_VERSION/BASH_VERSION, so it always concluded:

  - shell_name="bash"
  - config_file="$HOME/.bashrc"
- Symptom
On a zsh setup, the installer kept reporting:

Shell config: /Users/pcstyle/.bashrc

- and wrote the guard into .bashrc instead of .zshrc.
- Fix
Detection was changed to prioritize $SHELL's basename (zsh, bash, etc.) and then:

  - Print the detected default
  - Explicitly ask: "Which shell config file do you want to modify?", with that default
prefilled

That should have been the initial design.

7. Uninstall script bugs

The generated ~/.no-npm/uninstall.sh had several concrete problems:

- Unbound vars under set -u
It referenced PREFERRED_PM/GUARD_FILE in a way that, combined with set -u, caused:

PREFERRED_PM: unbound variable

- until the script was refactored to bake in literal values at generation time and not rely
on unset globals.
- Illegal local at top level
It had local declarations outside of any function:

local backup_file=...

- which is simply invalid and threw:

local: can only be used in a function
- Permissions not set
At one point the uninstall script was written but not made executable, giving:

permission denied: ~/.no-npm/uninstall.sh

- until chmod +x was added.
- Too aggressive sed ranges
The early uninstall logic tried to remove a "region" with sed range deletion, which risked
erasing more than the two lines the installer added. This was later tightened to:

  - Delete only the exact marker comment line
  - Delete only the matching source line

Matching the original mental model: "add two lines, later remove exactly those two."

---
8. macOS sed -i portability

- The initial script blindly used GNU-style:

sed -i 'pattern' file
- On macOS, sed -i needs an explicit empty extension:

sed -i '' 'pattern' file
- This caused errors like:

extra characters at the end of p command
- The fix was to introduce an OS detection helper and a single
cci:1://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:849:0-858:1 wrapper that
switches between -i '' on macOS and -i elsewhere.

Classic portability miss.

---
9. Backup philosophy vs expectations

There was a clear mismatch between desired behavior and what the script did for a while:

- Desired behavior
  - Small, predictable edits to shell configs
  - Only the comment and source line added/removed
  - Backups that are obvious and easy to reason about
- What the installer did for a while
  - Took full‑file backups before edits
  - Introduced backup and rollback machinery that felt heavy for "add two lines"
  - Initially made backup behavior noisy and not well explained

Eventually, the logic was pulled back toward:

- Always back up before touching a config
- Rollback uses those backups on failure
- Uninstall removes exactly the two lines it added

But it took several iterations to align with that simple mental model.

10. Complexity creep: from "simple installer" to full safety rig

Over time, cci:7://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:0:0-0:0
accumulated:

- Shell detection and validation
- OS detection and cci:1://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:849:0-858:1
- Dry-run mode that operates on temp copies of real paths
- Backup tracking for every touched file
- Automatic rollback on failure
- Guard script verification
- Installer checksum verification
- Config path validation and symlink checks
- Explicit disclaimer and "type accept" gating

The result was a ~1200-line bash script that is hard to read and debug, especially for
something that touches dotfiles.

This led directly to the split that now exists in the README:

- simple_install.sh: small, readable, no extra machinery
- safe_install.py: same safety ideas, but implemented in Python with clearer structure
- cci:7://file:///Users/pcstyle/projects_2/AI/no-npm/install.sh:0:0-0:0: full "everything
turned on" version, kept but explicitly labeled as heavy

11. Testing vs design intent

- Design claims
  - Interactive-only for safety
  - Dry run available
  - Backups and rollback
  - "Safe" text manipulation
- What actually flushed out the bugs
  - Running real installs/uninstalls on a macOS + zsh setup
  - Hitting TTY-only behavior when trying to pipe scripted answers
  - Seeing real errors for sed, local, unbound variables, wrong config file, and uninstall
failures

Many "safety" pieces only really worked correctly after several rounds of fixes based on
real behavior, not on the initial design.

---
12. The "nobody will read 1200 lines" problem

After the full installer was working, it became clear that the 1170-line script was
fundamentally at odds with the use case: people want to read what they're about to run
before it modifies their shell config. The length made that impractical.

Solution: three-tier approach

- simple_install.sh (170 lines)
  - Stripped all the verification, rollback, uninstall generation, acceptance warnings
  - Kept only: shell detection, guard generation, simple backup, dry-run mode
  - Single backup with timestamp, no restoration logic
  - Manual uninstall: delete the guard file and edit your config
  - Actually readable before running
- safe_install.py (Python rewrite)
  - All the safety features from the full bash version
  - Syntax validation, path checking, automatic rollback
  - Type hints and proper error handling
  - Easier to read and reason about than 1200 lines of bash
  - Casual comments ("bruh", "lol", "oh shit") instead of corporate tone
  - Confirmation prompt requires typing "yolo" instead of "accept"
- install.sh (the original)
  - Kept as-is for anyone who wants every safety feature in bash
  - Clearly labeled as the heavyweight option in the README

The README was rewritten to present all three upfront with clear descriptions of the
tradeoffs. Simple is recommended for most people. Python is there if you want safety
features but prefer readable code. Full bash is for completeness.

Short version

We started with a simple idea and grew a very complex bash installer that edits critical
dotfiles, while fighting portability issues (macOS sed), shell detection mistakes (bash vs
zsh), fragile text edits (sed ranges, malformed case blocks, bad function names), and
uninstall/backup behavior that didn't initially match the intended "add two lines, later
remove those two lines" model. Most of the serious issues only showed up when running the
script on a real macOS/zsh setup: it wrote to .bashrc instead of .zshrc, generated a broken
uninstall script, and hit sed, local, and unbound-variable errors.

Once the full installer was working, the 1200-line length made it unreadable for the
intended use case (review before running on your shell config). This led to creating
simple_install.sh (170 lines, minimal features, actually readable) and safe_install.py (all
safety features but in Python with casual comments and better structure). The end result is
three installers that cover different needs: simple and readable, safe and structured, or
full-featured bash.
```
